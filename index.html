Graph 可以組合 Agent 迴圈，也可以包含單次模型呼叫、工具或一般程式函式。涉及模型呼叫的步驟仍需要合適的 prompt 與 context。學新詞時，先辨認它多解決了哪一類問題。

既有基礎

Prompt Engineering

提示工程

設計目標、指令、範例、輸出格式和限制，讓模型在指定任務上產生較合用的結果。它不只等於扮演角色或字串模板，也可能影響工具選擇與多步工作。

情境、限制與證據怎麼用／怎麼理解

要求整理文章時，給出讀者、摘要長度、需引用的段落及兩個格式範例。後端則把任務要求和輸出契約一起設計。

容易誤會的地方

提示清楚仍不能保證事實正確、權限正確或輸出一定符合 schema；需用資料、驗證與評測補足。不要把要求公開思維鏈當成新模型的一律最佳做法。

證據類型：成熟實務

Context Engineering

上下文工程

管理每次模型呼叫能看到的指令、資料、工具描述、對話紀錄與任務狀態，決定哪些資訊值得占用有限上下文。

情境、限制與證據怎麼用／怎麼理解

閱讀公司手冊時，只送進相關段落、來源與任務背景；長任務把待辦和進度存在可再次讀取的檔案。

容易誤會的地方

長視窗不等於模型能正確使用所有內容。上下文壓縮可能遺失細節；使用者上傳 PDF 也不代表每個產品內部都採同一種 RAG。

名稱的起點常追溯到 2025-06-18 Shopify 執行長 Tobi Lütke 的貼文，以及一週後 Karpathy 的推廣（他形容這是把下一步剛好需要的資訊填進上下文視窗的技藝）；Anthropic 9 月的專文讓它成為工程用語。

證據類型：成熟實務

來源：S05 S59

Harness Engineering

Agent 執行環境工程

設計模型外圍的工作環境：工具、文件、程式庫約束、可觀測性、評測、權限、狀態與回饋，讓 Agent 能持續完成任務。常見的簡化說法是「Agent = Model + Harness」：凡不是模型本身的程式、設定與執行邏輯，都屬於 harness。

情境、限制與證據怎麼用／怎麼理解

編碼 Agent 可以讀規格、執行測試、看瀏覽器錯誤及保存進度，並依結果修正實作。

Mitchell Hashimoto 的定義最實用：Agent 每犯一次錯，就花時間補一個解法讓它不再犯——簡單的寫進 AGENTS.md，能程式化的做成腳本或檢查。health-rpg-backend 的 AGENTS.md＋ArchUnit R1–R7＋pre-commit 正是這兩種形式。

容易誤會的地方

沙盒只是其中一部分。Docker、Testcontainers、ArchUnit 或 Resilience4j 任一工具都不是 Harness 的完整定義；不存在人人必須使用的四大禁令。

2026-07 的原始碼研究觀察到：11 個主流 coding harness 都沒有引入通用 Agent 框架，也沒有用向量嵌入檢索程式碼，而是手寫非同步迴圈與確定性檢索（例如 grep）。這是現況描述，不是規範。

證據類型：官方工程案例

來源：S04 S29 S72 S76 S88

Loop Engineering

迴圈工程

設計會自己觸發 Agent 執行、以機器可檢查的條件判斷停止、把進度寫進外部狀態，並在必要時交給人的控制結構。實證研究的工作定義：以排程或事件觸發、重複呼叫 coding agent，每次執行都由機器可檢查的停止條件界定。

情境、限制與證據怎麼用／怎麼理解

夜間排程讀取 CI 失敗 → 在獨立 worktree 重現並修正 → 由唯讀 Checker 與測試判定 → 寫入狀態檔 → 達標開 draft PR；同一失敗簽章第 3 次或超出預算就停並通知人。完整對照見本頁「Loop 深入」。

容易誤會的地方

ReAct、重試與 TDD 都有較早來源；迴圈不等於永不停止，也不等於模型反省後就會自動變準。health-rpg-backend 的七步循環（早期文件稱 AIEC，取自團隊參考專案）是很好的實作範例，但不是業界標準名詞。實證研究在 36,710 個 repo 的樣本中確認 217 個自主迴圈（約 0.59%），不能推廣為整體開源採用率。狀態檔與預算檔的啟發式偵測未確認有效命中；另有 55 個候選 repo 在人工標註中可見目標或停止機制，顯示規則有偵測盲點；常見失敗是失控成本、無限修正迴圈與 verifier theater。Ralph 作者也明說不會把 Ralph 用在既有程式庫。

證據類型：實務文章＋預印本

Graph Engineering

圖結構工程

以顯式、動態、可演化的圖表示任務、Agent、依賴與系統狀態，協調多個能力元件共同完成目標。

情境、限制與證據

綜述把它定位為 System Intelligence，三根支柱是：任務組織（目標分解圖、工作流最佳化）、Agent 協調（能力圖、團隊組織圖、通訊圖）、執行期狀態管理（狀態紀錄、故障定位、失敗復原）。

怎麼用／怎麼理解

查資料、分析與獨立驗證可以分工；節點有狀態，邊決定依賴、分支與回饋路徑。

容易誤會的地方

研究中的框架不是既定職涯等級。知識圖、執行圖與任務依賴圖用途不同；有回圈的圖不是 DAG，LangGraph 可支援迴圈。

這個熱詞起於 2026-07-18 X 上半開玩笑的提問與 Hamel Husain 帶諷刺意味的文章；Turing Post 指出 loop 本來就是會回到前一節點的圖，狀態機、DAG、工作流引擎與 2024 年的 LangGraph 早已存在。把它當成「多個 loop 如何連接、失敗如何復原」的設計問題來學，而不是全新技術。

證據類型：研究預印本

Flow Engineering

流程工程

把一次生成改成可安排的多階段流程，例如分析問題、產生測試、生成程式，再依執行結果修正。AlphaCodium 論文已明確使用此名稱。

情境、限制與證據怎麼用／怎麼理解

程式題先分析邊界、建立測試案例、生成解法，最後跑測試而不是一次問出答案。

容易誤會的地方

不要把這個術語的來源直接歸給吳恩達；工作流設計的相近理念可以有多個倡議者，來源歸屬需要對應原文。

Compound AI Systems

複合 AI 系統

把模型、檢索、工具、驗證器與其他程式元件組合成系統，從系統層改善效果，而不只換更大的模型。

情境、限制與證據怎麼用／怎麼理解

文件搜尋服務由檢索、排序、回答、引用檢查與權限過濾組成。

容易誤會的地方

Spec-Driven Development

規格驅動開發

先把意圖、需求、計畫與任務寫成可追蹤規格，再讓編碼 Agent 依規格實作和驗證。GitHub Spec Kit 是代表工具之一。

情境、限制與證據怎麼用／怎麼理解

新功能先定義驗收條件及例外情境，再拆成小任務交由 Agent 執行。

容易誤會的地方

規格也會過時或互相矛盾。Spec Kit 1.0 在 2026 發布，並不代表規格驅動思想今年才出現；每個小修改都建大量文件也可能增加負擔。

Meta-Harness

自動搜尋模型外圍程式

把 Harness 程式本身當作搜尋對象，讓外層提出者利用歷次候選、分數與執行紀錄提出改進。

情境、限制與證據怎麼用／怎麼理解

容易誤會的地方

Agent Skills

可按需載入的技能包

用指令、腳本與參考資源封裝專業流程，讓 Agent 根據任務載入需要的部分。常以 SKILL.md 描述用途與操作方式。

情境、限制與證據怎麼用／怎麼理解

把產出公司報告的格式、資料檢查與匯出步驟保存成可重用技能。

容易誤會的地方

Skills 是能力與流程的封裝，MCP 是存取工具及資料的協定；兩者可搭配。載入技能不是把知識寫進模型權重。

ReAct / Agent Loop

推理與行動迴圈

模型根據任務與觀察決定行動，取得工具結果後繼續推進；推理和工具互動交替發生。

情境、限制與證據怎麼用／怎麼理解

容易誤會的地方

Durable Execution / Checkpoint

可恢復執行與檢查點

保存任務狀態及進度，讓長任務在中斷後恢復，或在人工審查後接續。

01決策模型與型別化輸出Jev 三原語 · 校準 · Java 介接閱讀專題

型別提問方式輸出重點與限制
Choice沒有先後等級的有限選項，例如 BILLING／SUPPORT／SALES。choice、各選項 probabilities、confidence。必須先定義可接受類別；仍可能選錯。映射 Java Enum 是應用適配層的工作，不是已證實的官方 JevClient 方法。

來源：S08

Score有順序的尺度，例如 0：無影響、1：可繞過、2：阻斷。等級索引的加權平均 score、各等級機率、confidence；HTTP 回應另包含 legend。若機率為 [0.1, 0.3, 0.6]，score = 0×0.1 + 1×0.3 + 2×0.6 = 1.5。它不是 150% 機率，也不代表 0～1 的風險。

來源：S09

Noul一個是／否命題，例如『是否需要查詢即時訂單？』。noul：命題為真的機率，介於 0 和 1；沒有另外的 confidence 欄位。由應用自行設定閾值。0.5 左右表示不確定，不該無條件轉成否；也不能把機率當作嚴重程度。

來源：S10

讀懂 confidence

它是答案機率分布的集中程度。Choice 依最高機率與均勻分布比較；Score 也考慮等級間距。高 confidence 仍可能在分布外資料上錯判。

Java 介接示意：把 Noul 機率轉成三態，而不是 boolean

這是自家 HTTP 介接的示意，不是官方 SDK，未編譯、未呼叫付費 API。重點：鎖定版本、不確定帶交給人、授權留在服務端。

// 示意：自建 Jev HTTP 介接（非官方 SDK；未編譯、未呼叫 API）
// 前提：Spring Boot 4.x RestClient、Java 25 record；JSON 由 Boot 4 的 Jackson 3 處理。
// com.fasterxml.jackson.annotation 是 Jackson 3 仍使用的註解套件（health-rpg R7 明列為例外）。
import com.fasterxml.jackson.annotation.JsonInclude;
import java.util.Map;
import org.springframework.http.MediaType;
import org.springframework.web.client.RestClient;

@JsonInclude(JsonInclude.Include.NON_NULL)
record Question(String type, Object instructions, Object criteria) {}
record SystemOneRequest(Object state, String model, Map<String, Question> questions) {}
record Answer(String type, Double noul, String choice, Double score,
              Map<String, Double> probabilities, Double confidence) {}
record SystemOneResponse(String model, Map<String, Answer> answers) {}

enum OrderLookup { NEEDED, NOT_NEEDED, UNSURE }

class JevOrderLookupClassifier {
    private final RestClient jev;   // baseUrl https://api.typesafe.ai，預設帶 Authorization: Bearer <API_KEY>

    JevOrderLookupClassifier(RestClient jev) { this.jev = jev; }

    OrderLookup classify(String userMessage) {
        var request = new SystemOneRequest(userMessage, "jev-1.13.0",   // 鎖版本，別用會移動的 jev-latest
            Map.of("needs_order", new Question("noul", "使用者是否要求查詢自己的訂單資料？", null)));
        SystemOneResponse response = jev.post().uri("/v1/systemone")
            .contentType(MediaType.APPLICATION_JSON)
            .body(request)
            .retrieve()
            .body(SystemOneResponse.class);  // 429／529 要用指數退避重試；逾時與重試另設

        double p = response.answers().get("needs_order").noul();  // 0～1；Noul 沒有 confidence 欄位
        if (p >= 0.80) return OrderLookup.NEEDED;      // 閾值用自家中文工單校準，不是固定值
        if (p <= 0.20) return OrderLookup.NOT_NEEDED;
        return OrderLookup.UNSURE;                     // 不確定帶：補問、改走規則，或交給人
    }
}
// 這只決定「要不要提供查詢工具」。真正查訂單前，仍由服務端以登入身分做授權（health-rpg R6 精神）。

要升級成 Loop Engineering 的最小補強（建議，未實作）

1. 先做只報告的觸發（L1）

用 Claude Code Routines、Codex Automations 或 GitHub Actions schedule，每天讀 CI 失敗與 loop-run-log 的 ACTIVE 項，只產出分診報告、不改程式。研究建議先 report-only，驗證者可靠後才放權。

2. 補上預算

每個 run 的 token 上限、每日次數、雲端帳號的硬性花費上限；用 /usage 的 Loops 明細檢查實際消耗。

3. Checker 自動化

把手冊 §9.4 的唯讀 Checker Prompt 做成 subagent（.claude/agents/ 或 .codex/agents/），只讀、只回報 findings。

4. 每個 run 一個 worktree

只能開 draft PR，不 merge、不 push main，與現行停止條件「未授權的自動 merge／push」一致。

5. 完成條件寫成輸出可證明的句子

/goal 的判斷模型不會自己跑指令或讀檔，所以條件要寫成「mvn -o -Dtest=X,ArchitectureTest test 輸出 BUILD SUCCESS 且 Failures: 0、Errors: 0」，並要求把輸出貼進對話；也可加上「或 20 回合後停止」。

6. 自主程度以能便宜驗證的程度為上限

L1 只報告 → L2 開 draft PR 由人審 → L3 才考慮無人值守。研究的說法是：你給 Agent 的自主程度，應以你能便宜驗證的程度為限。

  針對最新一次失敗的 backend workflow，用最小命令重現「第一個 root cause」，

先對齊案例的實際技術棧

health-rpg-backend 的 pom.xml 與版本基線：Spring Boot 4.1.1、Spring Framework 7.0.9、Spring Security 7.1.1、Java 25、Jackson 3（tools.jackson 3.1.5，ArchUnit R7 禁用 Jackson 2 runtime）、ArchUnit 1.4.2、Testcontainers 由 Boot BOM 管理。目前沒有 Spring AI 與 Resilience4j 依賴，所以常見說法的 Spring AI、@TimeLimiter 範例都屬「若要導入」的學習示意，不是現有程式。

ArchUnit 是 R1–R7，不是「4 大禁令」

現行 ArchitectureTest 共 7 條：R1 禁 Native SQL、R2 禁 JPA 關聯註解、R3 禁 Controller 直連 Repository、R4 命名規約、R5 禁環境時間（改注入 Clock）、R6 Request DTO 禁帶使用者身分、R7 禁 Jackson 2 runtime。常見說法第 4 條「審計欄位不變性」不在現行規則中；專案也明確不採用 FreezingArchRule。
